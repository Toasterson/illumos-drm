# Both DRM stacks on the ThinkPad X230

The X230 (Ivy Bridge, Intel HD Graphics 4000, PCI ID `8086:0166`) runs
OpenIndiana's display today through gfx-drm's legacy stack, `misc/drm` and
`i915`. This repository's stack (`misc/drm_core`) is installed beside it
for development. `drmadm(8)` chooses which one the machine loads; see
*Running beside the legacy stack* in the README for how it works.

## What to install

- From gfx-drm: `driver/graphics/drm` built with the reverse guard (gfx-drm
  branch `drm-coexist`: `misc/drm` refuses to load while `misc/drm_core`
  is loaded, and `devfsadm -C` removes stale `/dev/dri` links),
  `driver/graphics/drm-devlink` and `x11/library/libdrm` 2.4.134. Until
  that `driver/graphics/drm` is installed, OpenIndiana's `misc/drm` would
  load beside `misc/drm_core`, so do not load the new stack on the X230
  before.
- From this repository: `driver/graphics/drm-core` and
  `driver/graphics/drmadm` (published as in the comments of
  `packaging/*.p5m`), and the Intel driver `i915n` once it exists.

```sh
pkg install --be-name drm-both driver/graphics/drm driver/graphics/drm-devlink \
    x11/library/libdrm driver/graphics/drm-core driver/graphics/drmadm
```

Installing selects nothing: `i915` keeps the GPU, and the legacy stack
drives the display as before.

## Use the legacy stack for the display

```sh
drmadm select legacy
reboot
```

This excludes `misc/drm_core` and the new stack's drivers at boot and
gives `i915` the aliases of `driver/graphics/drm`. After the boot,
`devfsadm -C` removes `/dev/dri` links of the new stack's devices. `drmadm status` then
shows "legacy, since the last boot", `i915` and `drm` among the loaded
modules after Xorg started, and the `exclude:` lines of
`/etc/system.d/driver:graphics:drmadm`.

## Use the new stack for development

`select` refuses while a DRM module is loaded, and on the X230 Xorg holds
`i915`. Stop the display manager, unload the legacy modules, select and
reboot:

```sh
svcadm disable -t lightdm       # or the display manager in use
modinfo | egrep ' (drm|i915) '  # note the ids
modunload -i <i915 id>
modunload -i <drm id>
drmadm select new
reboot
```

If `i915` does not unload (the console may hold it), boot single user
(`-s`), where Xorg does not run, and select there, or select in another
boot environment with `drmadm -R` (below).

After the reboot `misc/drm` and `i915` are excluded; run `devfsadm -C`
once to remove the legacy `/dev/dri` links. Until `i915n` is
installed, `select new` leaves the Intel aliases unbound (it says so), the
GPU falls back to `vgatext`, the console stays in text or firmware
framebuffer mode, and there is no `/dev/dri` device for the GPU; the
new stack's test drivers (`cdrmnull`, `rdrmnull`) work as on any machine.

## Go back

```sh
drmadm select legacy
reboot
devfsadm -C     # after the boot: removes the new stack's /dev/dri links
```

Before removing the new stack's packages, run `drmadm select legacy`: the
fragment is drmadm's, not a packaged file.

## Recover from a bad selection

- Boot the previous boot environment from the loader menu (a selection
  changes only the running one), or select in a boot environment that is
  not running:

  ```sh
  beadm mount <be> /mnt
  drmadm -R /mnt select legacy
  beadm umount <be>
  ```

- Skip the fragment for one boot: boot with `-a` and answer the question
  "Name of system file" with `/etc/system`. The kernel then reads that
  file but none of `/etc/system.d` (`mod_askparams()` clears the
  self-assembly file), so nothing is excluded for that boot. Other
  fragments are skipped as well; this is for recovery only.
- Remove the selection in single user mode (`-s`):

  ```sh
  rm /etc/system.d/driver:graphics:drmadm
  bootadm update-archive
  reboot
  ```

  The Intel aliases stay where the removed selection put them; run
  `drmadm select legacy` afterwards.

`pkg verify driver/graphics/drm` reports the `i915` aliases as missing
while the new stack is selected. `pkg fix` would give them back to
`i915`; run `drmadm select new` again afterwards.
